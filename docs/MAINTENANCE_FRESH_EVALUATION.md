## 对照方法

两组使用同一 `deepseek-flash` 本地连接、固定源码、维护工具、顺序工具执行、报告校验、停止和上下文裁剪规则。唯一实验变量是系统提示：一组使用通用编程提示，一组使用 RepoCare 提示。提示长度会影响同一裁剪规则下的可用上下文，不能把它表述为相同字节长度的上下文。

每个阶段上限为二十四次请求、四十八次工具、一百八十秒，单次输出上限 8192，temperature 为零且不自动重试。h11 与 cattrs 先运行通用提示组，boltons 先运行 RepoCare。没有向模型提供独立检查失败后的修正建议，也没有继续训练或修订本批候选。

这是共享 RepoCare 工具与运行时的系统提示消融，不能代表与零工具 DeepSeek、Claude Code、GitHub Actions 或完整第三方产品的比较。单次探索与不同案例间的请求数量不能证明稳定提效。

## 源码供给修正与 PR 阻塞

原评测脚本把约 570KB 的 cattrs 源码提前放进任务缓存，未读取文件也占用产品预算。首次结果保留，并在再次请求模型前记录修正说明。诊断重跑保持目标、源码内容、顺序、预算与判据不变，只按固定 Git blob 请求按需供给缓存。

源码快照默认采用这一方式，`--eager-cache` 可用于复查旧记录。Git blob 的大小、SHA-1、路径与凭据筛查仍保留。模型读取固定快照之外的文件或准备 PR head/base 内容时仍可能需要 GitHub；重跑不是完全离线的模型实验。

隔离评测的 `pilot` 身份没有继承用户 GitHub 登录。保存 PR 对照时实际收到 GitHub 403，错误文本无法独立区分权限与额度，因此不把其唯一原因推断为限流。原始待确认计划和重跑失败都保留。单独准备依赖及测试 PR 本身，不能补记为上述阶段自行完成。

## Docker 结果

h11 的 RepoCare 原生方案未经修改完成两版各三次执行。原版目标每次出现约定故障，候选的计划命令每次通过，环境指纹一致，共享判读为目标观察到改进。

额外回归区域仍显示两条命令中一条存在失败：整份新增测试文件包含原版预期失败的目标，另一条 `test_helpers.py` 在两版通过。该记录不表示候选引入新回归，也没有被删去以提高通过指标。独立检查是另一次实验，产品原生记录没有独立来源标记，导出继续显示未记录。

通用提示组把 CSS 要求的首个故障写为缺少 `add_stylesheet`，但该测试先调用同一 setup 的 `add_javascript`。执行者没有确认这个已知不准确的要求。其生产补丁另行通过独立检查，不因此追认整个原生计划。

独立 h11 实验中，原版两个检查一失败、一通过，两组候选均为两通过。cattrs 独立实验检查两个 union 顺序、attrs 等价性及正常唯一字段选择：原版一失败、一通过，已有 PR 候选两通过。每个独立实验只执行一次；不能称为三次稳定验证或模型新修复。

cattrs 使用项目配置和依赖组，未禁用 conftest、插件选项或覆盖 pytest 配置。Python 3.12 环境保留一条 `typing_checkers` 未识别警告，没有据此声称配置全部兼容。

## 当前交付边界

本批的代码、CLI 和默认测试进入仓库，真实模型与容器实验使用隔离数据库，未向上游发布评论或 PR。默认检查不调用付费模型。自动浏览器此前受到策略限制，本次没有换通道绕过，也没有完成实际页面点击和视觉验收。

后续应先完成带登录或完整固定文件供给的 PR 主流程，减少无效重复读取并真实校准故障信号，再增加预先保留的新输入。当前材料支持展示目标验证、主动澄清、依赖准备及失败记录，尚不足以宣称稳定自主交付、总体成功率、维护者采用或优于通用助手。
