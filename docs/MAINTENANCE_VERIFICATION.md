# 需求、改动与对照验证

Issue 和 PR 详情中的“准备需求对照”使用现有维护任务。Agent 提议逐条要求、原文引用、生产改动路径、pytest 命令和预期断言信号。服务端检查引用与路径，维护者在两组执行前分别核对。没有真实执行记录时，页面保持待验证。

实现入口为 `src/server/workbench/maintenance-verification.ts`、`src/server/agent/tools.ts`、`src/shared/lib/maintenance-verification.ts` 和 `src/features/workbench/maintenance-verification.tsx`。共享协议位于 `src/contracts/maintenance-verification.ts`。

## 支持范围

- 公开 GitHub 仓库中的 Python/pytest 计划，复用现有隔离 Runner。
- Issue 使用已保存的候选补丁。测试文件改动同时应用到原版和改动版，生产代码仅应用到改动版。
- PR 要求完整读取所有变更，最多四个文件，每个不超过 20KB。当前支持修改和新增普通文本，不支持删除、重命名及二进制。
- PR 从固定 base 构建两组环境，根据完整 base/head 文件内容应用全部候选改动。测试改动在两边共享，因此原版是“base 加同一份测试”，不是原始 base 的逐字节副本。
- 依赖清单、锁文件和执行配置变化不进入此对照。大 PR 继续使用原有分块审查，不自动获得执行结论。

原文匹配只说明引用存在。需求与代码、断言之间的语义关系仍由维护者核对。新增测试或全部命令通过本身不能证明问题已解决。

## 页面阅读

Issue 详情将“修复与验证”放在分诊建议和原始讨论前，并提供区域跳转。内嵌工作区按读取依据、候选补丁、对照执行、阶段结论展示已有记录；阶段标记不代表源码已完整阅读或修复已获批准。下一步依据当前方案、任务状态和执行记录选择，查看补丁及审阅计划不调用模型，模型操作在按钮下方明确说明。

需求对照分别展示目标要求、额外回归、测试来源和独立验收范围。`verificationCoverage` 只有在两版已核对、版本指纹匹配、全部尝试及同一环境记录完整且对应命令都通过时，才将额外回归标为通过。没有安排、执行中、环境受阻、失败、依据不足和历史过期分别保留。它不改变目标要求的局部改进判据，也不将额外回归推断为完整测试覆盖。

原模型方案没有人工验收来源时明确显示未记录，不将模型生成的共享测试当成独立验收。维护者可在同一详情中另行提供 pytest 测试，保留原方案并生成独立保存的待确认对照。原文、生产路径、测试及逐次日志在每条要求内展开，原始版本和候选版本的完整计划在“审阅与执行两版计划”中分别确认。历史方案、阶段说明和源码依据按需展开；任务停止后保留已有结果。已消费的执行依据早于本次执行完成时间时，下一步会要求重新读取结果。

Markdown 导出包含覆盖说明与额外回归命令；现有 JSON 导出增加 `coverage` 字段，保留目标判读和原始执行记录。界面与导出使用同一纯函数计算覆盖状态，独立验收及完整回归的限制不会因目标通过而隐藏。

## 人工提供的验收

在当前需求对照下展开“添加人工验收测试”，提供一个至多20KB的Python文件、所选要求对应的目标函数、实际预期失败标记、正常行为函数及来源说明。函数使用顶层`test_`名称。原方案缺少依赖时，可在折叠区域提供基于仓库声明的受限pip准备命令，仍须预检和单独确认。至少选择一个目标和一个正常行为，不能复用同一节点。系统生成独立路径，测试在两版相同，仅候选版加入原候选的生产文件。此入口暂限根目录计划、至多三个生产文件和一个测试文件，不修改原模型测试和执行结果。

来源保存在`acceptanceSource`，包括声明、记录时间、内容SHA-256及原方案指纹。提供者可以声明测试未交给生成候选的模型，也可明确已经看过候选；系统无法证明作者身份、盲测条件或真实独立性。不得仅凭声明计算独立准确率。原测试和人工测试分别显示结论与未覆盖范围。

保存不调用模型、不执行代码。两版依然分别要求环境检查、逐条核对及执行确认，HTTP确认保留最新GitHub版本检查。原方案、规则或生产补丁变化会使关联验收过期。运行中的方案不可替换，最多保存三版。原始代码、测试、计划和指纹仍可导出，不允许从客户端上传“测试已通过”的结论。

`prepare-maintenance-acceptance.ts`仅在隔离pilot数据库中保存人工方案，要求`--reviewed`；`execute-maintenance-pilot.ts --artifact=acceptance --reviewed`沿原有队列与Runner执行。CLI不覆盖浏览器点击或HTTP的最新GitHub核对，不能用CLI结果冒充完整页面验收。

## 计划与确认

`prepare_verification` 通常接收 `requirements`、`regressionCommands` 和可选 `setupCommands`，服务端生成 Python、`test` 模式及 `all-steps-pass` 计划，再经过原有命令校验。Runner 已有 pytest，不必重复安装。只有预计在原版失败的缺陷进入 requirements；正常行为与完整套件放入 regressionCommands。高级 `planJson` 与这些快捷命令参数不能混用。两种输入方式均不执行代码，也不放宽安装路径及断网限制。

预期失败信号必须对应测试最先触发的实际错误。测试先断言盐值再调用序列化时，首个失败可能是 AssertionError，不能直接复用 Issue 后续调用的 TypeError。尚未确认和执行属于任务状态，不属于计划缺失依赖；真正缺少的环境条件仍必须列入 missingInformation。

### 执行阻塞与结论范围

计划和阶段报告用 `missingInformation` 记录阻止当前命令执行的缺口，例如缺少必需依赖。可选 `scopeLimitations` 记录未覆盖的行为，例如只检查一个接口、未运行完整套件。范围说明不会单独阻止限定检查。模型工具和阶段提示均说明这一区分，结构定义见 `src/contracts/execution-readiness.ts`、`src/server/reproduction/plan.ts` 和 `src/server/agent/report.ts`。

旧计划的缺失条目默认继续阻塞。维护者可以在“核对阻塞与范围”逐项勾选并填写至少八字的理由，将不影响当前命令的条目归为范围限制。服务端不根据文字关键词自动解除阻塞，也不修改原计划或方案指纹。复核记录保存原条目、索引、理由、时间及计划摘要，每个来源最多十次。阶段报告更新后使用新的报告版本，先前复核不再生效，历史记录仍保留。

`src/server/agent/readiness.ts` 在事务中检查账户、当前方案、项目规则和任务更新时间。仅两版均未确认时可以调整分类。页面、Markdown、JSON 导出及 Agent 的执行读取分别保留有效前置条件和范围说明。人工分类不能解除环境预检发现的阻塞。

### 固定 Runner 环境预检

维护 Agent 的 Python 测试计划在 HTTP 确认执行前要求环境预检。点击“检查运行环境”创建独立的 `environment-preflight` 队列任务，原测试计划继续等待确认。Worker 在断网、源码只读的容器中运行镜像自带的 `reproduction/preflight.py`，使用隔离 Python 解释器。它读取固定源码与候选写入的数据，不应用补丁、不安装依赖、不导入项目模块，也不执行测试收集。

检查内容包括实际 Python、pytest 版本，计划版本要求，以及 `pyproject.toml` 的 Python、pytest 与构建依赖声明。pytest命令按当前执行目录候选配置的优先级读取最低版本、`required_plugins`和已知pytest-cov参数；支持pytest原生TOML、INI、pyproject、tox与setup配置，显式`-c`单独读取，不合并低优先级配置。插件检查只查询镜像的发行包元数据，不加载插件；缺包且无安装计划时阻塞，有准备计划时标为待核对，明确禁用所需插件时仍阻塞。命令覆盖配置、完整配置发现和自定义插件行为仍需实际核对。

静态扫描覆盖命令中显式指定的 `.py` 文件、祖先 `conftest.py` 和有限的无条件顶层导入。候选新增或修改的文件以虚拟内容参与检查。unittest命令不会因pytest的覆盖率参数被阻塞。文件、导入和输出均有限额，达到检查上限时保留未知项。

| 结果 | 确认规则 |
| --- | --- |
| 已检查所列条件 | 维护者仍须核对检查结果、范围及原执行计划 |
| 有待核对项 | 展示构建后端、未安装的计划依赖或静态未知项，要求显式核对 |
| 存在阻塞 | 禁止确认执行，例如未安排安装的必需顶层导入缺失或 pytest 版本不符 |
| 未完成或过期 | 重新预检，不沿用缺失或失败结果 |

预检结果绑定计划 SHA-256、固定提交和 Runner 镜像 ID，有效期三十分钟。确认接口再次检查绑定及人工复核时间，Worker 在执行前再次核对实际镜像。两版可以分别预检；一版已入队不阻止另一版的环境检查。普通复现、贡献路径和直接调用验收脚本没有统一强制使用这项 HTTP 前置流程；带有预检引用的执行仍会检查镜像和计划绑定。

预检成功只说明所列静态条件已检查。目录级完整收集、条件导入、生成模块、动态插件和外部服务仍属于未知范围。准备步骤计划安装的包显示待核对，不冒充已经安装；准备联网未启用时继续阻塞。其他语言暂不提供这项预检。实际测试依旧必须单独人工确认。

行为测试位于 `tests/workbench/execution-readiness.test.ts`。可信静态检查器的容器用例位于 `tests/workbench/preflight-python.py`，不进入默认付费或 Docker 测试路径。公开案例的环境检查索引见 [2026-10-17-readiness.json](evaluation/2026-10-17-readiness.json)，它不改变先前候选的修复结论。

每组记录固定源码、PR head、补丁、共享测试、两组计划、需求来源和有效规则版本的指纹。每条要求使用明确的 pytest 文件与用例节点；可以另加完整测试集命令。显式目标测试及符合支持命名规则的测试改动在两边共享。相同内容复用已有方案，修订后旧方案保留但不可再次确认。后台运行中的调查不能同时确认执行，以免覆盖人工审阅的方案。

维护者查看补丁和共享测试后，逐条勾选要求及故障信号，再确认执行。服务端核对所有需求标识、计划指纹、当前项目规则和最新 GitHub 上下文。输入变化要求重新准备。PR 使用其 head/base 校验，Issue 使用分支提交及讨论版本校验。

确认只将任务入队。执行器固定镜像 ID，准备依赖后关闭网络，分别记录每次尝试的命令、退出码、有限输出和环境指纹。原始日志作为制品保存。执行租约失效的 Worker 不能覆盖当前状态，独立 Worker 工作目录避免恢复执行互相清理。

## 结果判读

“观察到改进”要求：两组计划均经核对，版本及上下文一致，所有尝试的环境指纹一致；原版对应命令每次以 pytest 断言失败结束，并包含已确认信号；改动版的计划内命令全部通过。指纹未知、记录不完整、测试收集异常或环境失败都不能得到该结论。

测试收集失败、导入依赖失败、准备失败与断言失败分别记录。超时、取消、未运行、证据不足和过期保留独立状态。两组原本都通过时，结果为未证明改进。任何一次改动后目标用例失败，展示仍失败。

额外回归命令若在同环境的原版全部尝试中通过、候选全部尝试中发生断言失败，覆盖区域明确显示“候选引入回归”，并把继续调查指向该正常行为。目标通过仍不能接受该候选。任一环境、确认、完整性或故障类型条件不满足时，不作这种归因；原版本身也失败只显示回归存在失败。页面、Agent 执行读取和导出复用同一判断。

页面提供逐条要求及每次输出，支持 Markdown 说明和带执行记录及制品索引的 JSON 导出。读取、轮询和导出不调用模型，不自动查询新的 GitHub 提交。导出属于记录中的固定版本；规则变化或已知业务输入变化会提示过期。

执行结束后，页面根据已保存记录给出下一项调查：环境阻塞先查依赖和收集日志，候选失败沿目标用例定位，原版未命中时核对测试与来源，记录不足时先补环境或回归依据，观察到改进后整理覆盖边界。维护者点击“继续此项调查”才调用现有维护 Agent。Agent 收到对应执行标识、要求、生产路径与失败命令，先读取执行结果，再提出候选修订。历史过期、执行中和未核对方案不提供此入口；新执行仍需人工确认。这是证据驱动的阶段衔接，不是无人值守的自动修复循环。

本流程不评定完整测试覆盖率，不批准合并，不自动关闭 Issue。测试和项目代码可以存在错误或互相影响；机器判据只能说明选定范围的观察。代码补丁可下载，自动代码 Draft PR 仍属于后续能力。

## 贡献路径与 Python 准备

受支持的安装命令使用 `python3 -m pip install --target .repocare-python --no-compile`，随后选择根目录 `-r requirements.txt`、`-r requirements-dev.txt`、`-r requirements-test.txt`、`--no-build-isolation .`，或 `--group test`。本地项目可以选择最多三个声明的扩展，例如 `--no-build-isolation .[test,dev]`。扩展和组名仅接受受限标识符，不能指定其他路径、URL 或附加安装选项。依赖组来自根目录 `pyproject.toml`，扩展与依赖组分别使用 pip 的标准解析机制，见 [pip install](https://pip.pypa.io/en/stable/cli/pip_install/)。

Runner 使用独立虚拟环境，其工具版本及下载哈希列在 [python-requirements.txt](../reproduction/python-requirements.txt)。当前配置包括 pytest 9.0.2、pip 25.1.1、setuptools、wheel、hatchling 和 hatch-vcs。构建镜像时只安装经过哈希校验的 wheel，并运行 `pip check`。镜像 ID 仍是执行时固定的环境标识，不把基础镜像标签当作不可变版本。

根项目安装使用 `--no-build-isolation`，需要 Runner 已有兼容构建后端；该选项的责任边界见 [pip 构建系统说明](https://pip.pypa.io/en/stable/reference/build-system/)。预检发现根项目安装所需后端缺失时阻塞，直接从 `src` 运行则保留警告。清单能确定扩展或组不存在时预检阻塞；动态扩展声明保留未知。包含其他组的声明只标记静态未知，由 pip 在实际准备阶段解析。其他后端、系统库、Python 版本和插件组合仍可能受阻。

Python 安装可能执行项目构建代码，仍需人工审阅并在受限容器准备阶段运行。npm 安装继续附加禁止生命周期脚本的选项。依赖联网配置保持默认关闭，详见 [隔离执行](REPRODUCTION.md)。

验证时优先从仓库根和 `src` 导入源码，再读取本次目标依赖目录。每个阶段的 `dependencies.json` 记录 Python、内置工具及最多三百个目标目录发行包的名称与版本，超限明确标记。数据来自发行包元信息，不导入项目模块，也不保存下载 URL。环境指纹包含该记录摘要；目标目录安装了另一版 pytest 时分别保留内置与目标版本。它不等同于每个第三方 wheel 的内容锁定，未锁版本的项目依赖仍可能随注册表变化。

计划明确声明简单 Python 版本前缀且与 Runner 不符时，执行保持受阻。贡献路径页面只把有实际步骤结果的准备步骤标为完成。PR 对照按固定 base SHA 获取源码，不要求 fork 中的分支在上游存在；普通 Issue 的显式标签仍可供 VCS 构建后端生成版本信息。

独立测试放在 `tests/` 内仍会加载其祖先 `conftest.py`，可能依赖额外包；只使用标准库的测试正文不代表整个收集过程无依赖。缩小范围时保留原套件未验证的限制，不禁用原项目配置来伪造全量通过。Windows 下载及恢复源码使用单次 Git 命令的 `core.longpaths=true`，不改用户的持久 Git 配置。

Humanize 固定版本的真实 VCS 版本生成、cattrs 声明依赖组安装及正常行为检查见 [新案例实测](MAINTENANCE_FRESH_EVALUATION.md)。`scripts/accept-python-preparation.ts` 提供显式 `--reviewed` 验收；只有额外传入 `--allow-network` 才启用该次准备联网。它使用隔离数据库与制品目录，不改变 Web 服务的持久配置，也不提供模型调用。

## 按固定预检声明准备环境

`reproduction/preflight.py`使用现有`tomllib`和安全文本读取，列出根目录已声明的requirements、项目、至多八个依赖组及八个扩展。未知、动态或不受支持的名称不生成安装选项。返回`preparationOptions`只代表读到声明，不代表已安装、兼容或测试通过。

旧`tool.poetry.dev-dependencies`在pytest预检中单独提示，当前不转换其版本约束或生成安装命令。根项目安装不等于安装开发依赖；缺失pytest插件仍按实际配置阻塞或要求核对。需要受支持的依赖声明或具备所需插件的Runner，不能通过删除覆盖率参数宣称环境已准备完成。

Agent通过`read_execution`取得独立返回的`preparationSource`，可在`prepare_verification`中提交`preparationFrom: {jobId, optionIds}`。服务端从原预检的选项解析实际命令；该方式不能与手写`setupCommands`或高级`planJson`混用。准备来源必须属于同一任务、固定版本及规则，计划指纹一致，预检在三十分钟有效期内；至多选择四个不重复选项。未知选项、改写的命令、其他账户和过期记录均拒绝。

服务端将选中的声明、命令和预检ID保存为交付物的执行依据。原模型方案保留，新方案重新预检并分别人工确认两版执行；网络、Runner和原执行限制继续生效。旧预检没有选项时，可重新预检或依据已读取声明显式提供命令，不能推断选项不存在就表示无需依赖。

## 验收边界

源码、静态检查和生产构建不能证明真实模型的需求提取正确，也不能替代 Docker、跨版本回归或浏览器交互验收。真实效果需要使用当前产品版本和固定案例单独记录。受控样例、真实历史输入和维护者采用分开统计，详见工作区执行计划。

受控场景、人工候选和后续真实 Agent 候选的实际范围与失败结果见 [维护链路实测](MAINTENANCE_ACCEPTANCE.md)。人工审阅协助的限定要求成功不代表无人值守修复，不将同一历史案例的多轮探索合并为独立样本成功率。
