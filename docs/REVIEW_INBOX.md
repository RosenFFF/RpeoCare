# Issue / PR 统一收件工作区（2026-10-05）

## 设计依据与选择

参考成熟维护型系统的布局原则，而不是照搬模板：
- GitHub Primer Action List：单列记录，主文本与辅助信息有一致层级，每条记录一个明确动作。
- IBM Carbon Data Table：搜索、过滤、结果统计和批量动作归属于同一个数据工作区；列头明确区分字段。

结合 RepoCare 现有中性灰与深青配色、侧栏与文档工作台，不新增 UI 框架。用响应式 CSS Grid 表达表格式收件列表（记录实际是可键盘操作的 button），不冒充原生 table。全宽列表按数据量自然收缩，详情另行进入全宽工作区；不再组合左右等高面板、PR 卡片网格、自动进入唯一 PR 和巨大空详情。

## 信息结构

### 共同骨架

项目与模块标题 → 一个收件工作区 → 快捷视图 → 搜索/维度筛选/排序 → 结果统计及相关操作 → 列头与记录 → 页码 → 点选记录后进入详情。

- 0 条：一个空状态，区分未连接、读取失败、筛选无结果、当前页无记录。
- 1 条：一个全宽数据行，不自动进入详情或调用模型，也没有配套空白详情卡。
- 多条：统一行式结构，不再散成重复卡片；移动端每行分为标题区和紧凑字段区。
- 筛选计数、搜索、分类和批量动作均只针对当前 API 页，界面明确标注“当前页”。
- 返回详情前的列表，保留筛选、排序及页码并恢复滚动/键盘焦点。

### Issue 维度

问题类型、优先级和处理状态是独立字段。快捷视图提供全部、未分诊、待补充、准备复现、高优先级。类型与优先级优先读取维护者确认值，否则使用 AI 建议；来源可见。未分析不能被推测为某个类型或低优先级。原文更新时显示过期标记。

批量分诊仅处理当前筛选下的未分诊/过期记录，最多 12 条，不处理被隐藏的其他类型。

### PR 维度

变更类型：依赖更新、文档、缺陷修复、功能、其他。基于标题/标签的轻量规则识别，明确注明非 AI 审查结论。Open 与 Draft 是另一个状态维度，不能和“是否已审查”混同，也不能因 Open 推断可合并。

head SHA 不可读取时显示“待读取”，不编造数量或分析状态。现有 head/base 固定、CI、Diff 证据、结构化发现与人工筛选/版本绑定发布逻辑保持不变。

## 工程组织

- `features/workbench/review-inbox.tsx`：Issue/PR 共用列表交互。
- `features/workbench/inbox-model.ts`：维度语义及轻量分类规则，纯前端共享定义。
- `features/workbench/review-inbox.css`：新的列表与详情工作区布局，不依赖旧卡片/双栏覆盖链。
- `git-items.tsx`：保留服务调用与已有详情组件，切换列表/详情，不展示占位详情。

## 验证范围

业务测试覆盖人工确认优先、无数据不虚构分类、PR 类型与 Draft 分离。浏览器覆盖宽屏/窄屏/深色、0/1/多条、错误与空状态区别、筛选/批量范围、返回原筛选和键盘焦点，以及现有分诊、复现和 PR 审查回归。截图数据为测试 fixture，不代表线上用户或真实模型结果。

## Issue 详情分诊布局（2026-10-07）

Issue 详情不再把完整分诊和人工维护功能堆在正文右侧，避免短正文与高侧栏形成整列空白。阅读顺序改为：横向分诊摘要 + 准备度/下一步 → 全宽讨论原文/译文 → 维护者确认与维护动作。正文很短时各区域自然收缩；长正文仍可滚动阅读，不人为用占位内容补空白。

首屏保留类别、优先级、置信度、建议动作、摘要和准备度；判断依据/阻塞项、实际/预期/环境、缺失/已有信息/建议标签三个分组采用原生 details 按需展开，不截断或删除分析。不同 Issue 切换时折叠状态重置。正文和主要建议使用14px、表单/动作13px、说明12px，废除详情区原9–10px微字号。下一步动作在准备度卡固定位置显示，不使用悬浮遮挡或嵌套滚动侧栏。

新样式位于 issue-detail.css，均以 issue-detail-layout 为范围，仅作用于 Issue 详情。PR详情、收件列表、复现面板和后端分析/确认/发布逻辑不变。窄屏单列，原文/译文纵向阅读，原生折叠可键盘展开；维护者确认不隐藏，权限和确认规则保留。本文仅记录布局变更，不将AI准备度分数作为真实复现结果。
