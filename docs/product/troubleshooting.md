# 常见问题

优先保留错误摘要、发生页面和任务状态，再按现象排查。不要用清空数据库、删除密钥或反复发布来尝试修复问题。

## 页面打不开或任务一直排队

| 现象 | 先检查 | 下一步 |
| --- | --- | --- |
| 浏览器无法连接 | 启动终端是否退出、访问端口是否一致 | 按部署章节启动完整服务，使用终端显示的实际地址 |
| 端口被占用 | 是否已经运行另一实例 | 复用已有实例或改用空闲端口；不要结束身份不明的进程 |
| 页面正常但体检不开始 | `/api/health` 的 worker 状态 | 确认使用 `npm start` 或 `npm run dev`，且 Worker 与 Web 使用同一数据库 |
| PR 审查或维护调查排队 | Agent Worker 日志 | 确认 Agent Worker 正常运行；健康接口不检查它的就绪状态 |
| 进度迟迟不刷新 | 后台任务状态、代理对 SSE 的缓冲 | 重新打开任务查看持久状态；管理员检查代理配置 |

## 仓库或分支读取失败

核对 GitHub 仓库 URL、所有者、仓库名及分支是否存在。私有仓库检查当前身份和仓库授权；GitHub 限流时等待恢复，或由管理员配置读取凭据。连接了错误项目时，先切换项目再查看任务，不能用旧项目报告解释新项目。

PR 搜索仅针对当前加载页；分支搜索针对已加载分支。找不到条目时检查分页、筛选条件和合并目标分支，不要立即判断数据丢失。草稿搜索则覆盖当前项目的匹配草稿。

## 模型保存成功但调用失败

检查服务地址、协议、模型名称、API Key 权限及服务商额度。网络超时、限流、协议不兼容和工具调用失败需要分别处理。先运行连接测试，成功后再重试业务任务；测试本身也可能计费。

密钥无法解密时，检查是否更换了 `REPOCARE_MASTER_KEY`，或恢复数据库时遗漏了配套 `.model-key`。不要删除旧密钥重新生成来“修复”，这会使旧连接继续无法解密。

## 登录、邮件或授权异常

GitHub 回调失败时，核对浏览器访问地址、`REPOCARE_APP_URL` 和 OAuth 应用的 `/api/auth/github/callback` 地址，包含端口和协议。邮箱收不到邮件时检查垃圾邮件、SMTP 配置和服务端发送错误，避免连续申请造成混淆。

切换登录方式后看不到历史数据，先确认是否进入了不同身份。匿名、邮箱和 GitHub 身份不会自动合并。

## 审查结果不完整或已经过时

打开任务的覆盖范围，区分失败块、截断和未审文件。有失败块时先排查模型错误，再按页面提供的入口重试失败部分。PR 新增提交后，旧 head 的结果只能用作历史参考，需要新审查。

CI 未知不等于成功；AI 审查完成也不等于 CI 完成。两者分别查看。

## Docker 验证无法执行

依次确认 Docker 正在运行、执行镜像已构建、功能已启用、复现 Worker 在线。附带 Compose 不包含复现 Worker；只启动 Compose 无法直接完成隔离验证。

若依赖准备受阻，先看日志中缺失依赖或网络限制，再调整经审阅的计划。超时、环境缺失和测试断言失败含义不同，应保留原始结果。不要把环境错误记为“Bug 已修复”或“Bug 不存在”。

## 草稿无法保存或发布

保存冲突时先比较当前服务端版本，合并所需内容后再保存。目标仓库有新提交时重新核对来源，必要时重新生成草稿。

发布不可用时检查 GitHub 仓库授权、实际写权限和确认选项。如果状态显示“结果待确认”，先打开 GitHub 核对是否已经出现对应 PR 或评论，避免重复创建。若远端仍无法核实，保留任务标识和错误信息交给管理员处理。

## 向管理员反馈

提供页面、操作步骤、预期结果、实际结果、时间、任务标识，以及脱敏后的错误摘要。不要提供 API Key、Cookie、Authorization 请求头或完整 `.env.local`。管理员应先查看对应服务日志，再决定重试或恢复。
