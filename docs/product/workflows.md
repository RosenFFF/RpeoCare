# 工作流与最佳实践

先选一个可判断完成与否的维护目标，再串联需要的模块。下面的场景是操作范例，不是预先生成的真实运行结果。

## 补齐项目协作资料

**目标示例**：让贡献者知道如何安装、测试和提交修改。

1. 固定目标分支完成体检，阅读 README、CONTRIBUTING 或模板相关检查项。
2. 选择有证据支持的缺口，生成文档草稿。
3. 核对命令是否来自真实项目清单，删去模型猜测的功能、地址和流程。
4. 如需确认新人能执行，审阅贡献路径计划后运行隔离验证。
5. 将相关文件草稿合并审阅，确认后创建 Draft PR，继续走项目自身审查流程。

**完成标准**：草稿内容与项目一致，必要命令有证据，交付目标正确。体检分数变化可作为辅助，不能代替内容审阅。

## 处理一个 Bug 报告

**目标示例**：判断某个输入是否触发报错，并给出有依据的回复或修复候选。

1. 阅读 Issue 的环境、输入和复现步骤，缺失信息先整理成回复草稿。
2. 分诊后继续调查源码，记录相关路径和提交。
3. 审阅复现计划的命令、依赖、预期失败信号，确认后在 Docker 中执行。
4. 复现流程会进行多次尝试；查看稳定性和每次证据。环境受阻、网络失败或依赖缺失应单独处理。
5. 有候选补丁时，核对补丁与原要求，再执行支持范围内的双版本对照。
6. 把结论及剩余不确定性写入回复草稿，人工确认后发布。

**完成标准**：区分“稳定复现”“未复现”和“环境受阻”，明确结论适用的版本与条件。未复现不能证明用户报告不存在。

## 审阅一项代码改动

1. 选中目标 PR，先理解作者意图、关联 Issue、base/head 与 CI。
2. 开始 AI 审查后查看实际覆盖范围；大型或截断的 Diff 需要补充人工审查。
3. 对每条发现追到源码和变更位置，删除误报、重复意见和无证据推断。
4. 有新提交时重新审查；不能把旧 head 的结论直接贴到新版代码。
5. 生成并编辑 COMMENT 草稿，语气聚焦可执行问题，说明证据和建议。

**完成标准**：评论中的每个问题都能由维护者解释，未审范围明确。是否批准、请求修改或合并仍在项目的 GitHub 工作流中决定。

## 判断对照验证是否有说服力

基线失败而候选通过，且失败对应目标需求，才支持“该改动改善了目标行为”。如果基线和候选都通过，只能说明本次测试未区分改动；如果依赖安装失败，不能据此判断补丁正确与否。

同时查看正常输入的回归结果，避免只修复一个示例却破坏常规路径。人工提供验收测试时记录来源及编写方式；填写来源声明本身不证明测试独立或充分。

## 控制成本和工作量

- 先做基础体检和人工筛选，再对需要的 Issue/PR 发起模型任务；查看页面不会自动等于开始 AI 审查。
- 一次处理一个边界明确的问题，先解决连接或环境错误，再重试任务。
- 重用已有报告与证据；PR 仅失败块需要重试时，不必从头重复全部审查。
- 根据设置中的实际调用与 token 用量判断开销。服务商未返回成本时，不把空值当作免费。

## 保留可以复查的交付记录

每次交付保留仓库、分支、提交、源 Issue/PR、审阅后的内容及验证证据。共享日志和报告前移除密钥与不应公开的项目资料。

维护者应能回答三个问题：建议来自哪里，验证了什么，哪些仍未验证。建议在发布前让另一名维护者阅读关键结论；单人维护时也应逐项重新核对。
