# 项目维护 Agent

`src/server/agent` 为维护流程提供 pi 工具循环，分诊和文档生成按需读取源码，深入调查保存检查点。PR 入口采用 [持久化分块审查](PR_REVIEW_WORKFLOW.md)，跨文件源码核对留在详情的深入调查动作中。`maintenance-support.tsx` 把依据和方案放在业务详情，导航没有独立 Agent 模块，旧 `/agent` 跳转概览。进入页面、查看依据及轮询不调用模型。

## 使用方式

连接仓库并配置支持工具调用的默认模型，然后使用原有维护动作。

| 位置 | 使用方式 |
| --- | --- |
| Issue 详情 | 开始分诊时按需核对源码；「修复与验证」可准备深入调查、补丁和隔离验证方案 |
| PR 详情 | AI 审查时补充关联源码；「变更影响核对」继续调查调用关系与需求影响 |
| 体检报告 | 原有规则及内容研判保留；「改进方案」对报告固定提交核对跨文件依据 |
| 文档草稿 | 生成时核对项目实现与命令；「改进影响核对」读取当前已保存的草稿版本，与基准源码比较 |

源码核对依据默认折叠，包含实际读取片段、固定提交及限制。深入处理只在点击具体动作后开始，仍使用当前账户配置的模型。方案和执行结果留在发起页面；可以补充线索、停止、继续。已保存的项目约定可在同一处查看和停用。

Issue 和 PR 的深入工作区将当前阶段与一个主要后续操作放在前方，补丁、对照和执行计划直接关联。查看方案与刷新记录不调用模型；准备、继续调查及读取结果形成结论会调用模型。页面以保存的交付物和执行记录计算进度，不把模型计划里的“完成”当作执行成功。具体覆盖和结果阅读方式见 [需求与对照验证](MAINTENANCE_VERIFICATION.md#页面阅读)。

计划和阶段报告分别记录真正执行缺口与结论范围。旧条目可以保留原文后由维护者填写理由复核。Python 计划的确认前静态环境检查由现有复现 Worker 执行，预检和复核都不调用模型。支持范围及确认规则见 [执行准备](MAINTENANCE_VERIFICATION.md#执行阻塞与结论范围)。

## 原操作中的只读调查

PR 分块调用使用固定的有界 Diff，不走此工具循环；详情中的深入核对继续使用源码工具。

`research.ts` 为 `issue-triage`、`pull-request-review` 和 `file-draft` 创建请求内的 pi 会话，只暴露目录、文件、指定路径搜索、协作上下文、提交检查、历史知识和证据重读工具。会话不进入后台队列、不写补丁、不执行代码；调用方把真实读取的依据随分诊结果、审查报告或草稿保存。旧报告仍可查看，重新分析使用源码调查。

单次操作最多 6 轮模型请求、12 次工具调用和 70,000 字符工具返回，总请求期限为 60 秒，单轮模型最多 35 秒。原输入仍有 100,000 字符边界，最终文本最多 30,000 字符。用量按真实返回的每轮输入、输出 token 计入现有统计。

不能固定源码时保留原输入分析，并记录未补全源码的限制。PR 正式发现仍只接受原始可见 Diff 的行号和原文；额外源码用于理解上下文。PR 与 Issue 在保存前核对来源是否更新。文档生成按体检提交读取；已保存草稿的深入核对同时绑定草稿 ID、版本和基准提交，版本变化后重新发起。

## 调查与交付

`read_project_rules` 读取当前账户、仓库的维护者已确认规则，保留版本及来源。规则作为维护要求，不改变工具权限；`policy` 证据不算源码读取。配置与确认见 [项目专属规则](PROJECT_RULES.md)。

工具实现位于 `src/server/agent/tools.ts`，源码访问位于 `repository.ts`。

| 能力 | 行为与边界 |
| --- | --- |
| 目录与源码 | 固定 commit 及 tree/blob SHA；目录分页，按路径和行读取；只在指定文件做字面搜索 |
| 协作上下文 | 绑定任务的 Issue 或 PR；按字符分页读取已捕获的上下文；保留来源更新时间 |
| GitHub 检查 | 查询固定 SHA 的 Checks/Status；不等同于 RepoCare 实际运行测试 |
| 调查依据 | 返回证据 ID、原文、提交及读取时间；报告校验 ID 是否属于此任务；语义正确性仍需审阅 |
| 项目知识 | 用户选择证据并明确保存；按账户、仓库隔离；提交不同标为历史知识；支持归档 |
| Issue 回复 | 生成本地草稿，进入原有草稿工作台审阅及确认发布；生成前核对 Issue 更新时间 |
| 补丁 | 每版最多四个文本文件、合计十二处替换，每文件 20,000 字符；同文件原文必须唯一匹配且片段不重叠；新增文件要求完整目录确认路径不存在；只保存差异与完整替换内容 |
| 复现 | 复用现有计划校验器及 Docker 执行器；生成计划不执行；当前只支持公开仓库的 Issue 任务 |
| 补丁验证 | 为同一提交创建原始版本、应用补丁后的两个计划，使用相同测试命令；分别审阅确认后执行 |

验证计划使用 `test` 模式及 `all-steps-pass` 判据，每个版本独立执行三次，全部命中命令通过判据才标为通过。原始版本与补丁版本的结果需分别读取；命令通过只说明计划中的命令通过，不能证明全部问题修复。执行结果保留尝试记录和制品摘要，工具可以读取这些机器事实，界面可下载经过 SHA-256 校验的制品。源码、评论和检查结果不能替代运行证据。Agent 计划保留任务归属，不混入 Issue 详情的普通复现列表，确认在发起页面核对当前方案版本。

每类交付物最多保留三版，任务内可以读取失败结果并修订补丁、验证计划与回复。修订补丁仍针对原始提交生成完整替换方案；历史计划保留证据，但不能再确认执行。补丁可以在对应页面审阅、下载，然后在对应提交的开发分支处理。代码补丁尚未接入 GitHub Draft PR 发布，也不直接修改宿主机工作目录。对照沿用固定输入的依赖准备；依赖清单或锁文件改动需要在开发分支另行验证。Issue 和支持范围内的 PR 可以调用 prepare_verification 准备逐条需求与共享测试的双版本计划，边界及确认流程见 [需求与对照验证](MAINTENANCE_VERIFICATION.md)。PR 调查不替代现有证据化审查的逐项确认与评论发布流程。

`propose_patch` 默认保留当前候选中未触及的文件，可分阶段添加生产代码和测试。省略 `basePatchId` 时，替换片段匹配原始提交，同文件须包含所需完整修订。提供当前 `basePatchId` 时，片段匹配该版候选，服务端保留原始文件作为最终 Diff 的 before；过期候选 ID 被拒绝，执行基准始终是原始提交。`replaceAll: true` 表示显式丢弃旧候选未触及文件，提交完整新方案。文件数、唯一匹配、片段不重叠和三版上限仍生效。

`read_patch_file` 按行读取当前有效候选，返回补丁 ID、修订号和未执行标记。候选内容不生成原仓库证据 ID，不能据此声称测试通过。`read_verification_environment` 返回内置执行器的声明，包括自动加入 `PYTHONPATH` 的根目录、`src` 和目标依赖目录；它不调用 Docker，不证明当前镜像、版本或额外依赖就绪。计划根据实际源码及执行输出核对环境；仅待确认、待执行和既定范围限制不应填成缺失前置条件。

`submit_report` 以结构化参数校验并保存阶段结论，成功后停止本阶段的后续模型请求。发现引用只能使用当前任务真实证据 ID，补丁和验证交付物 UUID 不充当证据。没有具体发现时可提交空 findings，并在 summary 说明已保存方案和待执行状态。旧的最终 JSON 报告仍兼容；报告通过结构与引用校验不等于语义正确。

已有问题原文和源码依据时，最后两次请求仅用于提交报告及一次校验纠错，工具额度同时保留纠错空间；总请求和工具上限不变。阶段提示列出真实证据编号，报告被拒后要求按原编号重新提交，不自动补全、替换或接受错误引用。小预算或缺少上下文时仍可能没有足够纠错机会。

预算耗尽或报告校验失败时，运行时在现有对话与提示中保存“系统阶段记录”，仅列已保存依据、当前交付物和预算数量。它不采用被拒报告的内容，不生成有效报告、不将任务标成完成，也不证明补丁或测试正确。已有模型报告和失败记录保留，新的继续操作仍由用户发起。

## 持久化与恢复

`store.ts` 在现有 SQLite 中创建 `maintenance_tasks`、`maintenance_messages`、`maintenance_workers` 和 `maintenance_memory`。任务按账户、仓库及用户选择的分支隔离；模型配置使用现有主密钥加密，公共任务数据只含模型选择元数据。

Worker 以 30 秒租约领取任务，每 5 秒续租。过期任务最多自动领取三次，随后暂停；继续由用户触发。每个完整模型轮次保存清除隐藏推理和服务商诊断正文的消息检查点。重读源码使用同一提交和缓存。交付物与关联草稿或执行计划在同一 SQLite 事务保存，恢复时按内容指纹复用已生成版本，避免重放产生重复草稿。

补充消息单独持久化，Worker 保存快照不会覆盖它们。阶段结束在事务内检查尚未消费的消息，存在消息时重新排队。取消及租约接管使用 Worker 身份和有效期约束，旧 Worker 不能恢复已停止的状态。

消息消费按实际提交给模型且成功结束的请求记录，支持 SDK 的字符串和文本块消息。已注入但未随请求送出的补充消息保留待处理；提交阶段报告时到达的新要求不会被算作已经处理。

`core.ts` 为体检、请求内调查和后台深入处理共享 pi 的串行工具执行及关闭隐藏推理的运行默认值。业务入口继续使用原有分诊、审查和草稿接口，源码调查及持久会话由服务端装配。

## 资源边界

后台深入处理初始预算为 24 轮模型请求、48 次工具调用，每次 Worker 执行最多 180 秒，单次模型请求最多 40 秒。手动继续最多累计 96 轮、192 次工具调用。每账户最多三个排队或运行中的任务。

每次请求会附加服务端阶段检查点：已有证据、剩余请求、当前有效补丁和对照方案。证据不足时继续读取；用户要求修复且已有源码依据时提示使用最小唯一片段提交补丁；已有补丁时提示准备对照或列明阻塞。该提示不替代模型判断，也不保证模型会完成交付。输出被截断时保留独立的长度诊断，不再归为原因未知。实际试跑结果见 [维护链路实测](MAINTENANCE_ACCEPTANCE.md)。

`maintenance-progress.ts`为工具预算保留一个报告额度；最后一轮仍提供`submit_report`。已经读取问题及源码、且只剩最后三次请求时，工具范围收敛到保存候选、准备方案、读取已有候选/执行及报告，不再扩展源码调查。服务端调用钩子再次校验范围，不能通过输出隐藏工具调用绕过。该窗口使用原预算，不增加请求上限；诚实的未完成报告不计作修复成功。

跨仓库 DeepSeek 探索、人工反馈、环境阻塞及未通过候选见 [公开仓库维护实测](MAINTENANCE_FIELD_TESTS.md)。这些记录不能替代真实维护者采用或同条件通用模型对照。

模型实际返回的输入、输出 token 计入任务和现有使用量统计。上下文整理使用保守的应用字节预算，不代表精确 token 计数；整理保留目标、步骤、交付物索引、证据索引和完整的近期消息组，原始证据仍可通过工具重读。不估算服务商费用。

单个源码文件最多 120KB，任务源码缓存最多 600,000 字符，目录最多 15,000 个允许读取的文件，证据最多 100 项。超出范围、目录截断、读取失败和未知 CI 必须保留为限制，不能当作项目缺陷。敏感路径、符号链接、二进制和包含已识别凭据模式的文件不提供给模型；这不构成全面秘密扫描。

## 接口与运行

`GET /api/workbench/agent?kind=<kind>&number=<number>` 按当前项目、分支和业务对象查询最近调查；文档以 `anchor` 绑定报告或草稿版本。可传 `repoUrl`、`branch` 校验项目切换。`?id=<task>` 按归属返回详情与关联执行计划；不带上下文参数时保留任务摘要兼容接口。页面不提供独立任务管理入口。`POST` 支持 `create`、`message`、`resume`、`cancel`、`remember`、`archive-memory`、`confirm`。写操作沿用同源和会话校验；确认执行前重新核对分支 commit、Issue 更新时间和计划缺失信息。

`npm run dev` 和 `npm start` 同时启动 Web、体检、复现和维护 Agent Worker。维护 Worker 可独立使用 `npm run agent-worker` 启动；与 Web 共用工作目录、数据库和主密钥。Compose 包含独立 `agent-worker` 服务。复现与补丁验证仍需另行配置现有 Docker 执行器，Runner 源码变化后需重新构建镜像，再重启对应 Worker，详见 [复现执行器](REPRODUCTION.md)。

可以用 `REPOCARE_BUILD_DIR` 为生产构建指定独立的项目内输出目录；默认仍为 `.next`。它只改变 Next 构建目录，不改变数据文件与 Worker 配置。
