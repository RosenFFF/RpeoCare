# 维护链路实测：2026-10-16

## 后续真实模型验收

真实 DeepSeek Agent 已在同一个历史案例上生成生产补丁和测试，经人工核对及方案修订后完成双版本执行，再读取执行记录并保存结论。未提供给模型的独立测试也通过。它支持“限定要求下、人工审阅协助的维护闭环”，不支持无人值守修复、完整测试集通过或优于通用模型的结论。脱敏记录见 [真实 Agent 执行索引](evaluation/2026-10-16-agent.json)。

此次使用项目专用加密模型连接，官方 `deepseek-flash` 的两轮工具探针通过。安装的 SDK 目录只有 `deepseek-v4-flash`；适配器对官方 Chat Completions 地址继承其兼容配置，并保留请求模型 ID。SDK 实际载荷测试确认关闭推理时发送 `thinking: {type: "disabled"}`，符合 [DeepSeek 推理模式文档](https://api-docs.deepseek.com/guides/thinking_mode/)。没有据此断言此前失败只有一个原因。

| 探索记录 | 实际结果 | 后续处理 |
| --- | --- | --- |
| 官方别名适配后首跑 | 到达补丁工具，但多处修改不符合原接口边界 | 支持同文件多处唯一、非重叠替换，保留文件及版本上限 |
| 多处替换后的任务 | 保存生产补丁；旧依赖安装路径被校验器拒绝，报告引用也曾失败 | 增加简化 pytest 计划和类型化报告；人工核对故障信号后执行 |
| 首条完成的任务 | 两条缺陷要求的原版三次命中约定失败，候选三次通过；模型随后读取结果并完成报告 | 独立两项测试及三个相关测试文件通过；该组包含 66 项原测试和 3 项模型新增测试 |
| 新开任务的首次重跑 | 分阶段提交测试时覆盖了生产补丁，对照工具拒绝只有测试的候选 | 保留未触及的候选文件，显式完整替换仍可丢弃它们；增加回归测试 |
| 保留候选文件后的新任务 | 自行保存四文件候选及方案；人工指出首个断言与预期 TypeError 不符，模型修订为 AssertionError | 两条要求的对照三次均观察到改进，模型读取结果后完成；独立测试和三个相关文件共 70 项测试通过 |

这些探索保留失败记录，预算和工具实现发生过变化，不能把前后轮次当作同条件性能比较。人工反馈包括计划范围和预期失败信号的核对，未人工修改上述已通过候选的生产代码。独立测试由执行者在模型试跑前定义，没有作为 Agent 输入；它检查历史签名、正常盐值及篡改拒绝。模型生成测试和独立测试分开执行与记录。

第二个候选已占用四文件额度，因此独立测试追加到已有测试文件，保留模型的生产内容。该独立计划中的 70 项包括 66 项原测试、2 项模型新增测试和 2 项独立测试；独立目标和正常行为还分别执行。原始 Agent 方案只运行它提议的两个相关测试文件，不能把独立计划额外的覆盖归给模型。

Windows 工作区换行转换曾使评测缓存内容与 Git blob SHA 不一致。评测脚本现在从固定 blob 读取并验证内容 SHA；旧结果原样保留，不能把旧 `sourceDigest` 当成实际模型输入字节的证明。新脚本还记录缓存内容及关键实现文件摘要，历史记录中缺少的摘要不补造。

当前仍只有一个公开历史 Issue，正文含解释线索，重复执行不增加独立案例数。整个仓库的测试集、浏览器点击及最新 GitHub 上下文确认、真实维护者采用和通用模型对照仍未完成。以下内容保留较早验收时的结论和失败，不代表后续修订后的状态。

本次修订的 `npm run check` 已通过 ESLint、类型检查、156 项测试和生产构建。新增测试覆盖官方别名实际请求载荷、多处替换、分阶段保留补丁、结构化报告以及报告结束时新消息的消费边界。默认测试不调用付费模型；实际模型与 Docker 结果来自单独显式执行。

## 较早验收记录

验证器已在 Docker 中区分有效改进、无效补丁和环境故障，并在一个公开历史问题的限定范围内跑通服务端链路。真实 Agent 试跑没有产出可执行补丁，当前不能宣称自动修复闭环已经达到稳定交付水平，也没有证据证明优于通用模型。

## 环境与记录

- Docker Engine 29.8.2；Runner 固定镜像 `sha256:5658b273d25ad6ccc00537ddff00afa4d517dbf1acf68f3b8025bf0a850cb09a`。
- Runner 内 Python 3.12.3、Node 24.20.0。执行期断网、只读根文件系统、无额外 capabilities，并限制进程、内存和 CPU。
- 测试、历史执行和模型试跑分别使用隔离目录或 SQLite，不把案例灌入用户项目。模型沿用本地默认连接，凭据只在进程内使用。
- 每组重复三次用于检查判据稳定性；它们不是三个独立真实项目样本。
- 可复现脚本与判读逻辑进入源码；模型原始检查点、凭据、数据库和私人参考答案不公开。脱敏汇总见 [执行索引](evaluation/2026-10-16.json)。

## 受控验收

合成函数及测试只用于核对机制，不冒充社区真实需求。前七项各执行原版和候选版三次，使用相同测试。

| 场景 | 实际判读 | 与预设一致 |
| --- | --- | --- |
| 有效生产补丁 | 观察到改进 | 是 |
| 无效生产补丁 | 改动后仍失败 | 是 |
| 原本正常，仅增加注释 | 未证明改进 | 是 |
| Python 版本不符 | 环境受阻 | 是 |
| 缺少导入依赖 | 环境受阻 | 是 |
| 测试语法导致收集失败 | 环境受阻 | 是 |
| 目标通过，但正常行为回归失败 | 证据不足 | 是 |
| 本地 Python 包安装与导入 | pip 准备成功，断网验证通过 | 是 |

最后一项实际使用 `pip --target .repocare-python --no-build-isolation .` 安装本地受控包，随后通过目标目录导入。准备和执行均断网，依赖摘要一致。它没有验证外部注册表下载、其他构建后端或任意 Python 项目的兼容性。

本次候选生产补丁和额外测试由执行者人工核对，未使用未来修复文件作 Agent 输入。两组均加入同一份测试，只在候选组修改生产文件。测试检查历史签名兼容、往返解析、显式命名空间和篡改拒绝。历史正文自身含解释线索，因此它不属于答案完全未知的盲测。

| 计划 | 原版结果 | 候选版结果 | 整体判读 |
| --- | --- | --- | --- |
| 目标测试、正常行为测试、原仓库三个相关测试文件 | 目标三次命中约定失败；正常行为和 66 项原测试通过 | 三次均通过全部计划命令 | 限定要求观察到改进 |

缩小范围后的成功不能代替全量回归。旧依赖清单位于 `requirements/tests.txt`，超出当前根目录安装白名单，且旧依赖与当前 Python 的兼容性没有完成验证。保留该阻塞，未放宽测试、替换锁定依赖或把错误计为成功。

## 真实模型试跑

使用现有 `deepseek-flash` 连接、同一个历史 Issue 正文和固定源码。通用基线使用 pi Agent、同一组维护工具和权限，要求最小修复、回归测试和对照方案。每组最多 10 次模型请求、18 次工具、180 秒，单次输出上限为 4096；不允许上游发布或自动执行。

| 试跑 | 通用基线 | RepoCare |
| --- | --- | --- |
| 首组可配对记录 | 7 次请求，0 个补丁 | 8 次请求，0 个补丁，请求未完成 |
| 增加阶段检查点后的记录 | 6 次请求，0 个补丁，结果未完成 | 8 次请求，0 个补丁，输出截断 |

最早的单组试跑因评测脚本未消费初始消息而重入旧任务，不能用于配对比较；记录保留。修正脚本后重新试跑。通用组“SDK 已停止”不再直接算作任务完成，截断或报告解析失败会记录失败。

另做一次仅 RepoCare 的诊断，将单次上限增至 8192；8 次请求后仍未保存补丁，最后请求超过产品的 40 秒上限。这一诊断改变了预算，不计入同条件对照。所有轮次使用的源码和正文相同，但产品检查点实现有修订，不能跨轮合并为稳定性能指标。

这些都是一个历史输入上的探索性试跑，不是独立样本评测。没有真实维护者采用、准确率、人工节省时间或显著性证据。需要继续解决输出长度、延迟、上下文压缩后的重复读取及阶段交付，再扩大到预先选定的新案例。

## 本轮修复和后续门槛

修正了执行器租约和后台分块审查对应的过期测试；补充共享测试、断言信号、版本、环境、租约接管及 Agent 截断诊断的回归。界面内增加依据实际失败类型继续调查的入口，仍使用原维护任务，新计划仍待人工核对。浏览器自动访问曾被安全策略阻止，本轮未改用其他通道绕过，视觉与点击验收没有完成。

`npm run check` 的 ESLint、类型检查、145 项测试和生产构建通过。另检查了两份 Runner JavaScript 的语法。自动测试使用 mock 模型和临时数据库；上面的付费模型及 Docker 实测由独立命令显式运行，不混入默认测试。

下一轮以“真实 Agent 保存候选补丁及可核对方案”为首要门槛，再验证方案能否通过独立测试。现有人工候选的成功只支持验证器机制。暂不扩大语言、增加独立 Agent 模块或宣称完整自动修复。

## 复现命令

下列命令显式执行 Docker 或调用现有模型，不属于默认单元测试。需要 Node 24、Docker、当前 Runner 镜像；历史准备会只读下载公开源码和 Issue。外部服务和软件包的后续变化可能导致失败。

```sh
npm run repro:image
npm run accept:maintenance
npx tsx scripts/prepare-maintenance-case.ts
npm run accept:maintenance:workflow -- data/acceptance-history-scoped.json
npm run accept:maintenance:workflow -- data/acceptance-history-full.json
# 显式调用本机配置的模型；可能产生服务商费用
npm run evaluate:maintenance -- --run-models
# 单组更高输出预算的诊断，不作同条件对照
npm run evaluate:maintenance -- --run-models --repocare-only --max-output=8192
# 真实模型方案生成；仍不执行或发布，显式预算不作同条件基线比较
npm run evaluate:maintenance -- --run-models --repocare-only --max-output=8192 --turns=24 --tools=48
```

已有本地试跑可以通过 `scripts/continue-maintenance-pilot.ts` 接收审阅反馈，参数依次为 `data/model-pilot-*` 目录和 UTF-8 文本文件路径；这会再次调用原任务的模型。`scripts/execute-maintenance-pilot.ts` 的参数为同一个目录和 `--reviewed`，只执行当前、无缺失前提且不安装依赖的方案。先阅读实际补丁、逐条要求及故障信号再使用该标志。脚本直接调用服务端队列和执行器，不能替代产品 HTTP 确认的最新 GitHub 校验。记录中的失败及旧方案保留，不删除后重跑以制造成功率。

源码快照保留上游 BSD-3-Clause 许可证；案例输入和候选文件留在忽略的 `data/`。脚本不向上游仓库写入，不复制私人评测答案，也不修改当前用户模型连接。
