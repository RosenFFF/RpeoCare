# 维护链路实测：2026-10-16

验证器已在 Docker 中区分有效改进、无效补丁和环境故障，并在一个公开历史问题的限定范围内跑通服务端链路。真实 Agent 试跑没有产出可执行补丁，当前不能宣称自动修复闭环已经达到稳定交付水平，也没有证据证明优于通用模型。

## 环境与记录

- Docker Engine 29.8.2；Runner 固定镜像 `sha256:5658b273d25ad6ccc00537ddff00afa4d517dbf1acf68f3b8025bf0a850cb09a`。
- Runner 内 Python 3.12.3、Node 24.20.0。执行期断网、只读根文件系统、无额外 capabilities，并限制进程、内存和 CPU。
- 测试、历史执行和模型试跑分别使用隔离目录或 SQLite，不把案例灌入用户项目。模型沿用本地默认连接，凭据只在进程内使用。
- 每组重复三次用于检查判据稳定性；它们不是三个独立真实项目样本。
- 可复现脚本与判读逻辑进入源码；模型原始检查点、凭据、数据库和私人参考答案不公开。脱敏汇总见 [执行索引](evaluation/2026-10-16.json)。

## 公开历史问题

案例为 [ItsDangerous #237](https://github.com/pallets/itsdangerous/issues/237)，使用 2.0.0 的固定提交 `d101100c395958d67368b8c37d95a9c404598c2e`。问题涉及显式传入 `salt=None` 后的签名兼容性，官方 [2.0.1 变更记录](https://itsdangerous.palletsprojects.com/en/stable/changes/#version-2-0-1)记载了相关修复。

本次候选生产补丁和额外测试由执行者人工核对，未使用未来修复文件作 Agent 输入。两组均加入同一份测试，只在候选组修改生产文件。测试检查历史签名兼容、往返解析、显式命名空间和篡改拒绝。历史正文自身含解释线索，因此它不属于答案完全未知的盲测。

| 计划 | 原版结果 | 候选版结果 | 整体判读 |
| --- | --- | --- | --- |
| 目标测试、正常行为测试、原仓库三个相关测试文件 | 目标三次命中约定失败；正常行为和 66 项原测试通过 | 三次均通过全部计划命令 | 限定要求观察到改进 |
| 目标测试、正常行为测试、整个原仓库测试集 | 缺少 freezegun，三次受阻 | 缺少 freezegun，三次受阻 | 环境受阻 |

两种计划通过真实公开仓库下载、固定提交、入队确认、Worker 租约、Docker、逐次输出、制品索引和共享判读函数执行。测试脚本直接调用服务端函数，没有覆盖浏览器按钮、HTTP 确认时的最新 GitHub 校验或维护者可用性。

缩小范围后的成功不能代替全量回归。旧依赖清单位于 `requirements/tests.txt`，超出当前根目录安装白名单，且旧依赖与当前 Python 的兼容性没有完成验证。保留该阻塞，未放宽测试、替换锁定依赖或把错误计为成功。

另筛选过 [Click #3487](https://github.com/pallets/click/issues/3487)，固定候选的生产文件为 20,471 字节，超过当前单文件 20,000 字符／字节读取边界中的字节限制，因此未进入执行或成功率统计。

## 真实模型试跑

使用现有 `deepseek-flash` 连接、同一个历史 Issue 正文和固定源码。通用基线使用 pi Agent、同一组维护工具和权限，要求最小修复、回归测试和对照方案。每组最多 10 次模型请求、18 次工具、180 秒，单次输出上限为 4096；不允许上游发布或自动执行。

| 试跑 | 通用基线 | RepoCare |
| --- | --- | --- |
| 首组可配对记录 | 7 次请求，0 个补丁 | 8 次请求，0 个补丁，请求未完成 |
| 增加阶段检查点后的记录 | 6 次请求，0 个补丁，结果未完成 | 8 次请求，0 个补丁，输出截断 |

最早的单组试跑因评测脚本未消费初始消息而重入旧任务，不能用于配对比较；记录保留。修正脚本后重新试跑。通用组“SDK 已停止”不再直接算作任务完成，截断或报告解析失败会记录失败。

另做一次仅 RepoCare 的诊断，将单次上限增至 8192；8 次请求后仍未保存补丁，最后请求超过产品的 40 秒上限。这一诊断改变了预算，不计入同条件对照。所有轮次使用的源码和正文相同，但产品检查点实现有修订，不能跨轮合并为稳定性能指标。

这些都是一个历史输入上的探索性试跑，不是独立样本评测。没有真实维护者采用、准确率、人工节省时间或显著性证据。需要继续解决输出长度、延迟、上下文压缩后的重复读取及阶段交付，再扩大到预先选定的新案例。

## 本轮修复和后续门槛

修正了执行器租约和后台分块审查对应的过期测试；补充共享测试、断言信号、版本、环境、租约接管及 Agent 截断诊断的回归。界面内增加依据实际失败类型继续调查的入口，仍使用原维护任务，新计划仍待人工核对。浏览器自动访问曾被安全策略阻止，本轮未改用其他通道绕过，视觉与点击验收没有完成。

`npm run check` 的 ESLint、类型检查、145 项测试和生产构建通过。另检查了两份 Runner JavaScript 的语法。自动测试使用 mock 模型和临时数据库；上面的付费模型及 Docker 实测由独立命令显式运行，不混入默认测试。

下一轮以“真实 Agent 保存候选补丁及可核对方案”为首要门槛，再验证方案能否通过独立测试。现有人工候选的成功只支持验证器机制。暂不扩大语言、增加独立 Agent 模块或宣称完整自动修复。

## 复现命令

下列命令显式执行 Docker 或调用现有模型，不属于默认单元测试。需要 Node 24、Docker、当前 Runner 镜像；历史准备会只读下载公开源码和 Issue。外部服务和软件包的后续变化可能导致失败。

```sh
npm run repro:image
npm run accept:maintenance
npx tsx scripts/prepare-maintenance-case.ts
npm run accept:maintenance:workflow -- data/acceptance-history-scoped.json
npm run accept:maintenance:workflow -- data/acceptance-history-full.json
# 显式调用本机配置的模型；可能产生服务商费用
npm run evaluate:maintenance -- --run-models
# 单组更高输出预算的诊断，不作同条件对照
npm run evaluate:maintenance -- --run-models --repocare-only --max-output=8192
```

源码快照保留上游 BSD-3-Clause 许可证；案例输入和候选文件留在忽略的 `data/`。脚本不向上游仓库写入，不复制私人评测答案，也不修改当前用户模型连接。
