# RepoCare开源维护助手

## 摘要

RepoCare面向中小型开源项目维护者，围绕固定代码版本，将Issue需求、PR改动与执行证据组织为可审阅流程。系统内嵌pi Agent开展源码调查，结合项目规则、引用校验、共享测试双版本执行、环境预检和人工确认，辅助判断候选是否改善目标以及是否破坏正常行为。人工提供的验收测试另行保存来源声明、内容指纹和执行记录。

本报告为提交前审阅稿。已有探索性实测支持局部目标验证、候选回归拦截、合理澄清与环境阻塞识别；尚未证明稳定自主修复、总体优于通用助手、实际节省维护时间或真实维护者采用。正式报告须由负责人核对权属、第三方资源与AI辅助声明后冻结。

## 1. 问题与应用场景

维护者需要同时阅读Issue、PR、源码、测试和协作约定。AI能提出看似合理的改动，但模型生成解释、CI状态和实际验证是不同依据。候选可能满足某个目标却改变相反开关的正常行为；环境缺依赖也可能被误解为缺陷复现。产品主要帮助维护者在执行和交付前核对这些差异。

主要用户是项目维护者。贡献者继续通过现有GitHub协作流程提交材料。当前执行能力聚焦公开GitHub中的小型Python/pytest项目，体检和只读审查的范围更广，但配置识别不等于全语言修复。项目申报方向为AI开发工具与开源协作。

## 2. 产品流程与实现

产品包含项目概览、固定快照体检、贡献路径演练、Issue分诊、PR审查、文档草稿和受控交付。Agent嵌入业务详情，不设独立聊天模块。维护流程为：读取问题及规则、调查相关源码、保存候选、核对需求和测试、检查环境、分别确认两版执行、阅读结果并决定下一步。

Next.js Web与独立体检、维护和复现Worker共用本机SQLite。持久任务记录状态、检查点和交付物，租约阻止过期Worker覆盖结果。客户端只使用共享协议，仓库代码不由Web进程在宿主机执行。pi SDK提供模型与工具循环，项目实现业务工具、预算、证据与流程约束。

PR准备对照按固定head/base目录定位文件并复用已读取的Git blob，校验普通文件、大小、UTF-8、凭据线索和内容指纹。逐文件检查点支持读取受阻后继续；不能用浮动分支或不完整文件集合代替完整对照。执行确认时仍核对最新GitHub上下文。

界面采用统一浅色与青绿色主题。概览优先展示维护状态和操作，项目图按需展开；验证详情优先展示结论，再展开原文、差异、命令和日志。目标改善、正常回归、环境受阻、未知与过期分别表达，图形和动画不代替执行依据。

## 3. 自主设计与已有方案

本作品的自主设计重点是需求、改动、共享测试、逐次执行及版本指纹之间的关联，以及执行前置条件、结论范围与人工验收来源的分离。需求原文存在只说明引用有效；改动与断言是否真正对应，仍需要人工核对。

双版本对照将同一测试应用到原版与候选，生产改动仅进入候选。只有已确认目标在原版稳定命中约定断言、候选计划通过且环境记录一致时，才给出局部改进。正常行为在原版通过、候选失败时，结果突出候选回归。环境受阻与测试收集失败不能被计作目标复现。

人工验收建立额外对照，保留原模型方案与结果。来源记录包含说明、提交时间、测试内容SHA-256及父方案指纹。“未提供给模型”属于提交者声明，系统不据此证明作者身份或盲测。测试未运行、输入变化和未覆盖范围保持可见。

现有GitHub Agentic Workflows已有Issue分诊、澄清和相关问题检索；PR-Agent已有需求符合性和分块审查。项目不将这些单项能力宣称为首创。当前差异化主张集中于可核验维护流程与结果边界；其效果仍需更多预先固定的新任务和机制对照支持。

## 4. 验证方法

开发测试使用隔离数据库及mock模型/GitHub。真实模型与Docker实验单独显式启动，固定来源、预算、指纹与结果。目标测试、正常行为和完整套件分别统计，不把每次重试或同一案例的多版本计算为独立样本。

2026年10月17日的新输入批次包含h11 Issue #200、boltons Issue #500和cattrs PR #800。共享运行时、工具、安全约束与上下文裁剪规则，两组只改变系统提示，故属于提示消融，不能代表与完整第三方产品的比较。每阶段上限24次请求、48次工具、180秒，输出上限8192，temperature为0。公开正文含修复线索，且执行者已阅读，不是盲测。

完整实验记录保留在忽略目录，公开索引提供脱敏摘要、来源、指纹与本地制品位置。公开索引本身不是完整离线复现包。仓库另提供已知cattrs历史案例的自有检查代码和显式Runner复查入口，不调用模型；该示例不能再计为未见任务。模型请求量不等于账单，模型耗时也不等于人工处理时间。

## 5. 已有结果及限制

| 案例 | 已观察结果 | 结论边界 |
| --- | --- | --- |
| MarkupSafe #417 | 人工核对后原版目标失败、候选三次通过；相关套件37通过、17跳过 | 含人工介入，未验证跳过行为 |
| python-dotenv #256 | 独立检查发现初始候选破坏override=False，反馈后修订通过所列检查 | 原完整套件未验证，非首次自主成功 |
| Humanize #366 | 扩展测试81通过、1失败，保留失败候选 | 后续真实构建准备成功不证明旧候选已修好 |
| h11 #200 | 原生方案两版各三次，目标观察到改进 | 额外回归包含原版预期失败，不能称完整回归通过 |
| boltons #500 | 两组均保留维护者行为选择，无生产补丁 | 正确澄清，不计为自动修复成功 |
| cattrs PR #800 | 旧流程受源码供给及GitHub读取阻塞；固定源码复用后可保存计划 | 模型仍遗漏依赖命令；人工验收另行记录 |
| ItsDangerous #126 | 两组受限调查均未保存补丁，报告核验失败；另行原版检查目标失败、正常行为通过 | 保留失败，未得到模型候选对照 |
| Blinker #179 | 项目提示识别顺序未定义并保留维护者决策；通用提示先尝试改变约定，补丁被文件边界拒绝 | 同条件提示消融的小样本，未证明普遍优越 |

h11提示消融中，两组生产补丁均通过预先保留的独立检查。RepoCare组用13次请求保存计划，通用提示组用21次，但单个案例不足以证明稳定提效。通用组的预期首错不准确，执行者未确认其原生计划。cattrs的预加载与GitHub403诊断重跑不算新增案例。

同一cattrs PR在读取修正后的回归试跑中，首次15次请求保存方案；两次人工反馈后累计25次请求，模型说明仍与实际安装步骤不一致。静态预检阻止未准备依赖的执行；不能把这一过程称为首次自主交付。补充的人工验收使用先前固定的行为检查和声明内的依赖命令，实际验收中，原版三次目标断言失败且正常行为通过；候选三次两个节点均通过，六次环境指纹一致。只支持所列行为，未运行完整套件。

受限调查另行暴露了报告预算收尾问题。服务端为报告保留额度，并从实际预检声明解析选中的准备命令；相关约束通过mock及容器静态检查。新模型案例尚未证明该准备机制能稳定恢复失败计划。两任务之间修改了预算逻辑，不能合并计算效果率，详情见docs/MAINTENANCE_BOUNDED_EVALUATION.md。

## 6. 安全、开放与复用

常规体检只读仓库文件。受控执行使用固定提交、独立Worker和Docker；执行阶段断网，源码、计划、镜像及环境摘要进入记录。准备联网单独显式启用。Docker不可用时保持阻塞，不回退宿主机。人工确认仍是必要边界，这些限制不证明对所有不可信代码具有绝对隔离能力。

源码和部署说明、测试、脱敏实验索引构成可复用成果。完整运行数据、密钥、个人身份、模型检查点和私人对话不进入公共仓库。案例源码及协作内容按各自许可与权利边界处理。RepoCare自主代码经负责人选择采用Apache-2.0，正式文本与声明位于LICENSE及NOTICE；当前资源盘点不替代第三方许可义务复核。

主要第三方包括pi SDK、Next.js、React、SQLite、Docker、pytest、Diff与图表组件。模型通过用户配置API调用，记录中的deepseek-flash只是配置ID，不证明底层模型权重版本。核心版本、用途与自研边界见第三方资源说明及依赖清单。

作品使用Codex辅助代码开发、调查、测试、UI与文档；产品模型用于业务调查和方案提议。负责人需核对实际人工决策、修改、验证和共同权利人授权，按真实情况说明AI参与，不将生成内容当然认定为自主知识产权。

## 7. 部署、复查与后续

本地需要Node.js 24，按README使用npm ci及npm run dev。复现能力还需Docker Runner，依赖准备联网默认关闭。模型、OAuth与SMTP按需要自行配置。多Worker目前只支持同机共享SQLite，跨主机部署、多托管平台、全语言修复和代码补丁自动Draft PR不属于当前已验证范围。

工程复查使用npm run check。真实任务应按文档显式运行隔离pilot与验收脚本，不把付费调用纳入默认测试。复查必须同时保留固定输入、首次交付、人工反馈、失败、排除条件、实际预算、环境及未覆盖范围。

后续优先降低模型方案与实际步骤不一致的比例，补预先保留的新任务、首次使用者走查和新环境复现。正式录屏需展示实际操作与记录，脚本不能代替视频。材料冻结前核对许可、第三方清单、AI说明、评审访问链接和平台回执。
